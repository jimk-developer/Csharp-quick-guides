Handling What Goes Wrong

Even a carefully written program can encounter situations it cannot complete normally: a file that does not exist, a calculation that divides by zero, input that cannot be converted to the expected type. C#'s exception handling system gives you a structured, object-oriented way to detect these problems, respond to them, and clean up afterward, rather than letting them crash a program unpredictably. This guide covers what exceptions are, how try/catch/finally blocks work together, the Exception class's own useful members, how exceptions travel through a program's call stack, and how to build your own custom exception types.

⚠️ Exception Fundamentals

An exception is an error condition or unexpected behavior encountered by an executing program. Exceptions occur at runtime, while the program is actually running; errors caught while compiling a program, such as syntax mistakes, are not considered exceptions at all, since the program never even reaches the point of execution.

The Exception Hierarchy

In C#, all exceptions are objects that belong to, or derive from, the Exception class. Like every other class in C#, Exception itself ultimately descends from the single built-in root class, System.Object. C# defines more than 100 distinct Exception subclasses to represent many specific kinds of problems.

Branch of the Hierarchy Description
SystemException Covers exceptions predefined by the Common Language Runtime (CLR) itself, such as errors related to arithmetic, arrays, or type conversion
ApplicationException Historically intended for user-defined exceptions; current Microsoft guidance recommends deriving custom exceptions directly from Exception instead, covered later in this guide
You can deliberately trigger a SystemException just by writing code that contains an obvious runtime error, such as dividing an integer by zero; C# does not require any special setup to produce a genuine exception for testing or demonstration purposes.

Robustness, Fault Tolerance, and Mission-Critical Systems

Robustness is the degree to which a system is resilient to stress and able to maintain correct functioning even when something unexpected happens. Applications specifically designed to keep operating, possibly at a reduced level, even when some part of the system fails are described as fault-tolerant. Building fault-tolerant, robust applications matters most for mission-critical processes: tasks whose failure would have serious consequences, where the software simply cannot be allowed to crash outright.

According to the creators of C#, an event is considered infrequent for a program when it happens in less than roughly 1% of that program's executions. This distinction matters because exceptions carry more processing overhead than an ordinary conditional check, so they are best reserved for genuinely infrequent, unexpected situations rather than routine, everyday conditions.

🧭 Object-Oriented Error Handling

There are two general approaches to dealing with a possible error condition in a program.

Traditional Validation

Using an ordinary if statement to check for a problem condition before it can occur, such as confirming a divisor is not zero before performing a division.

Object-Oriented Exception Handling

Using the try, throw, and catch keywords to attempt an operation, signal that something went wrong, and respond to that problem separately from the normal flow of the code.

Managing a potential error with a conditional statement, rather than an exception, is most efficient when the error condition is common enough, or cheap enough to check for in advance, that paying the overhead of a full exception is not worthwhile; a simple, everyday check like confirming a divisor is nonzero fits this description well.

In object-oriented exception handling, when you anticipate that a procedure might run into a problem that prevents it from completing correctly, you try that procedure: you place its statements inside a try block. When a method actually detects an error condition while running, it throws an exception, signaling that something has gone wrong.

📋 Common Exception Types

Exception Type Thrown When
DivideByZeroException An integer value is divided by zero
IndexOutOfRangeException An array subscript falls outside the array's valid bounds
ArrayTypeMismatchException An attempt is made to store an element of the wrong type into an array
ArgumentException An argument passed to a method is not valid for that method
IOException A problem occurs opening, reading from, or writing to a file
OperationCanceledException An ongoing operation is aborted by the user
Dividing an integer by zero throws a DivideByZeroException, but dividing a floating-point value, such as a double, by zero does not throw any exception at all. Floating-point division by zero is well-defined in C# and simply produces a special result such as Infinity, -Infinity, or NaN (not a number), depending on the values involved.

🧱 The try/catch Structure

A block of code where something could reasonably go wrong should be placed inside a try block. A try block is legally allowed to contain any number of statements, including statements you are confident will never actually throw an exception; C# does not require every individual risky statement to have its own separate try block, one try block can safely surround several statements together.

Syntax: A Basic try/catch

try
{
    Console.Write("Enter a divisor: ");
    int divisor = int.Parse(Console.ReadLine());
    int result = 100 / divisor;
    Console.WriteLine("Result: {0}", result);
}
catch (DivideByZeroException ex)
{
    Console.WriteLine("You cannot divide by zero.");
}

How Many Types a catch Block Can Catch

A single catch block catches exactly one exception type, though that one type can be a general class, such as Exception itself, which then matches every one of its many derived exception types at once.

Multiple catch Blocks

A try block can be followed by several catch blocks in sequence, each one written to handle a different specific exception type. When an exception is thrown, C# evaluates the catch blocks in the order they are written, from top to bottom, and executes the first one whose exception type matches; every remaining catch block after that match is bypassed entirely for that particular exception.

Because catch blocks are evaluated in order and stop at the first match, placing a more general exception type's catch block before a more specific one's makes that later, more specific catch block unreachable, also called dead code: statements that can never execute under any circumstances, given the program's own logic. Always list more specific exception types before more general ones.

Syntax: Catching Any Type of Exception

catch (Exception ex)
{
    Console.WriteLine("An unexpected error occurred: {0}", ex.Message);
}

Writing catch (Exception ex) is how you begin a catch block that will receive any type of exception thrown, since every exception type is, directly or indirectly, derived from the Exception class.

Experienced professional programmers generally recommend against relying solely on the general Exception class in a catch block for real projects. Catching specific exception types whenever possible produces clearer, more intentional error handling and avoids accidentally swallowing problems the code was never designed to recover from.

If a try block runs to completion with no error at all, every catch block that follows it is bypassed completely; none of them execute unless an exception was actually thrown inside the try block.

🏷️ Exception Class Members

The Exception class provides several useful members for describing what went wrong.

Member Purpose
Message Read-only property containing a descriptive explanation of the exception
ToString() Overridden by the Exception class to provide a detailed error message, built in part using GetType() to include the specific exception class's name
StackTrace Read-only property listing the sequence of method calls, the call stack, that led to the exception

Example: Using Message and ToString()

catch (Exception ex)
{
    Console.WriteLine(ex.Message);
    Console.WriteLine(ex.ToString());
}

🔄 TryParse() Methods

C#'s built-in TryParse() methods, such as int.TryParse() or double.TryParse(), are the category of methods used to convert string data to another data type, such as int, double, or bool, without any risk of generating an exception. Each of C#'s built-in TryParse() methods returns a bool indicating whether the conversion succeeded, and delivers the converted value through an out parameter, rather than throwing an exception when the conversion fails.

Example: Avoiding an Exception with TryParse()

Console.Write("Enter a whole number: ");
string input = Console.ReadLine();

if (int.TryParse(input, out int quantity))
{
    Console.WriteLine("You entered {0}.", quantity);
}
else
{
    Console.WriteLine("That wasn't a valid whole number.");
}

🧹 The finally Block

A finally block is used for clean-up tasks that must occur no matter what happens in the try block above it. A finally block executes in every possible case: whether the try block completes normally with no problems, whether it ends abnormally with an exception that a catch block successfully caught, or even when an exception occurs that no catch block catches at all.

Syntax: try/catch/finally

StreamReader reader = null;
try
{
    reader = new StreamReader("inventory.txt");
    // ...read and process the file...
}
catch (IOException ex)
{
    Console.WriteLine("Could not read the file: {0}", ex.Message);
}
finally
{
    if (reader != null)
    {
        reader.Close();
    }
}

A finally block like this one is exactly the kind of code block you use to ensure that input- and output-related files are properly closed, regardless of whether reading the file succeeded or failed.

A try block followed directly by a finally block, with no catch block at all, is most appropriate when you want guaranteed clean-up to run but you are intentionally not handling the exception at this level; the exception is still allowed to propagate up to the calling method after the finally block's clean-up statements finish running.

If a try block includes three catch blocks and a finally block, that finally block still executes after any one of those catch blocks runs, after the try block completes with no error at all, and even if an exception occurs that none of the three catch blocks are written to catch.

Terminating a Program

The Environment.Exit() method, part of the System namespace, can be used to terminate an application immediately from anywhere in the code, regardless of where the call occurs.

🧵 The Call Stack and Propagation

The call stack is the memory location where the system stores the list of active method calls, tracking exactly which methods called which other methods and where execution should return to once each one finishes.

Propagating an Exception

When a method does not handle an exception it encounters, such as by having no matching catch block for it, that exception automatically moves up to whichever method called it, continuing upward through the call stack until some method along the chain catches it, or until it reaches the very top of the program uncaught and the program terminates. This process is called propagating the exception.

A method that does not handle a thrown exception simply lets that exception propagate to its own calling method automatically; nothing special needs to be written to make this happen; it is simply what occurs whenever a method has no catch block that matches the exception being thrown.

Reading a Stack Trace

The StackTrace property is most useful exactly when you need to trace the precise sequence of method calls that led up to an exception, in order to pinpoint where in the program the underlying problem actually originated.

Example: A Sample Stack Trace

at PaymentGateway.ChargeCard(Double amount)
at OrderProcessor.CompleteCheckout(Double total)
at CheckoutApp.Main()
Read a stack trace from the top down: the very first line shows where the exception was actually thrown, not the bottommost line. In the example above, the true source of the problem is inside PaymentGateway.ChargeCard(), not CheckoutApp.Main(); Main() merely sits at the far end of the chain of calls that eventually led there.

🛠️ Custom Exceptions and Rethrowing

Creating a Custom Exception

According to Microsoft's current guidance, you should extend the Exception class directly to create your own custom exception type, rather than extending ApplicationException, which older references sometimes recommended instead.

Example: A Custom Exception Class

class InsufficientStockException : Exception
{
    public InsufficientStockException() : base()
    {
    }

    public InsufficientStockException(string message) : base(message)
    {
    }

    public InsufficientStockException(string message, Exception innerException) : base(message, innerException)
    {
    }
}

These three constructors, a parameterless constructor, one accepting a descriptive message, and one accepting both a message and an inner exception, are the three recommended constructors to write when defining a custom exception class, matching the constructor pattern the base Exception class itself provides.

One constraint on throwing objects in C#: you can only throw an object whose type derives from the Exception class. An arbitrary object that has nothing to do with Exception cannot be used with the throw keyword.

Rethrowing an Exception

Rather than fully handling an exception itself, a method can pass a caught exception back up to whatever method called it, an action known as rethrowing the exception. This is done using the throw keyword by itself, with no expression after it.

Syntax: Rethrowing an Exception

catch (Exception ex)
{
    Console.WriteLine("Logging the error before passing it along...");
    throw;
}
Writing a bare throw; statement, rather than throw ex;, preserves the exception's original stack trace information, which is exactly why throw; by itself is the correct way to rethrow a caught exception.
