Responding to What the User Does

A GUI program spends most of its life waiting: for a click, a keystroke, a mouse movement. Rather than following a single fixed sequence from start to finish, event-driven programs respond to whatever the user happens to do, in whatever order they do it. This guide covers how events are raised and handled, the delegate objects that connect an event to the code that responds to it, how mouse and keyboard events work, and how to manage focus and shared behavior across several controls at once.

⚡ Event-Driven Architecture

When something interesting happens to an object, such as a button being clicked, that object is said to have raised an event, also described as firing or triggering the event. A GUI control that generates an event is called an event sender. Because these programs perform their tasks in response to user interactions like clicking buttons, rather than following one fixed sequence from beginning to end, they are described as event-driven.

📡

Event Sender

The control or object that generates, or raises, an event, such as a Button being clicked by the user.

🎯

Event Handler

Also called an event receiver: the method that executes in response to an event being raised.

🔌

Event Wiring

The act of connecting an event to the resulting actions that should occur when it fires, linking a sender's event to a specific handler method.

The act of calling an event method is described as raising the event; a program uses an event to notify a client of a class that some change has occurred within an object of that class, without the object needing to know anything about which specific methods will respond.

📮 Delegates

A delegate is an object that encapsulates a reference to a method, defined using the delegate keyword. A C# delegate is comparable to a function pointer in C++: a variable type that holds a method's memory address rather than an ordinary data value.

Syntax: Declaring and Using a Delegate

delegate void AlertHandler(string message);

static void PlayChime(string message)
{
    Console.WriteLine("Chime: {0}", message);
}

AlertHandler chimeHandler = PlayChime;
chimeHandler("Low battery");

Any delegate can encapsulate any method that shares its return type and parameter list; the delegate AlertHandler above can hold a reference to any method matching void MethodName(string), not just PlayChime().

For a static method, a delegate simply encapsulates the method itself, since a static method is not tied to any particular object and needs no object reference to be called. A delegate referencing a nonstatic instance method, by contrast, must also keep track of which specific object that method should run on.

🔗 Composed Delegates

Multiple delegates can be combined into a single composed delegate using the + or += operators. Invoking a composed delegate calls each of its underlying delegates in sequence, one after another.

Example: Composing Two Delegates

AlertHandler chimeHandler = PlayChime;
AlertHandler flashHandler = FlashLight;

AlertHandler combinedHandler = chimeHandler + flashHandler;
combinedHandler("Low battery");
// Calls PlayChime("Low battery") first, then FlashLight("Low battery")

After this assignment, calling combinedHandler(...) invokes both PlayChime() and FlashLight() in the order they were combined, even though combinedHandler is still just a single delegate variable.

Assigning one delegate directly to another, without combining them, uses ordinary assignment: secondHandler = firstHandler; makes secondHandler reference exactly the same method (or methods) that firstHandler already references.

🧷 Custom and Built-in Event Handlers

Declaring Your Own Events

To declare your own custom event, you use the delegate keyword to define the delegate type that describes the shape of the handler methods your event will accept, and then declare the event itself using that delegate type together with the event keyword.

Events are not required to be declared private. In fact, events are typically declared public precisely so that client code outside the class can subscribe its own handler methods to them; declaring an event private would prevent outside code from ever attaching a handler to it at all.

The Two-Parameter .NET Convention

Following .NET guidelines, an event delegate's signature is conventionally structured to accept exactly two parameters: an object sender parameter identifying the event's source, and an EventArgs e parameter (or a class derived from EventArgs) carrying any additional details about the event. This two-parameter pattern is a strong convention, not a hard requirement enforced by the C# language itself; C# does not require every event's delegate type to use any specific fixed number of parameters.

Example: A Custom Event Following the Convention

delegate void StockLowEventHandler(object sender, EventArgs e);

class Inventory
{
    public event StockLowEventHandler StockLow;
}

The EventHandler Delegate and EventArgs.Empty

The .NET Framework provides a predefined EventHandler delegate for events that carry no additional information beyond the sender itself, saving you from declaring a custom delegate for every simple event. The EventArgs class has a field named Empty, a read-only instance of EventArgs used precisely for this situation, when there is genuinely no extra event data to pass along.

Example: Using EventHandler and EventArgs.Empty

public event EventHandler StockLow;

// Raising the event with no extra information to send
StockLow?.Invoke(this, EventArgs.Empty);

🎛️ Control Component Events

Standard GUI Controls, such as Buttons and ListBoxes, already define a set of predefined events you can handle using exactly the same underlying principles that apply to a custom class's own events: a delegate connects the event to whichever handler method you write for it.

When you double-click a Button on a Form in Visual Studio, the IDE automatically generates the shell of that Button's Click() event handler method, wires it to the Click event for you, and drops your cursor right inside it, ready for you to add your own statements.

The generated method header for a Button's Click handler follows the standard two-parameter convention: its second parameter is an object of type EventArgs.

You do not need to examine and fully understand every line of code a control generates before you can use it. Visual Studio's IntelliSense and the Properties window's Events list expose the events and properties a control supports without requiring you to read through its full generated implementation first.

🖱️ Mouse Events

Mouse interactions, such as clicking, pointing, and dragging, are handled using the MouseEventHandler delegate, paired with a MouseEventArgs object that carries the details of the mouse action, such as which button was pressed and exactly where the pointer was located. Objects of the MouseEventArgs class can carry this information for mouse events on any control.

Mouse Event Occurs When
Click The user clicks the mouse within the control's boundaries
MouseLeave The mouse cursor leaves the control's boundaries
MouseUp A mouse button is released while the pointer is still within the control's boundaries

Example: A Mouse Event Handler

private void canvasPanel_MouseDown(object sender, MouseEventArgs e)
{
    Console.WriteLine("Clicked at X:{0}, Y:{1}", e.X, e.Y);
}

You can determine exactly where within a Form the user clicked the mouse pointer by reading the X and Y properties of the MouseEventArgs parameter supplied to the handling method, as shown above.

⌨️ Keyboard Events

An event resulting from a user's interaction with the keyboard is known as a key event. Depending on the specific event, keyboard event handlers are created using either the KeyEventHandler delegate, paired with a KeyEventArgs parameter, or the KeyPressEventHandler delegate, paired with a KeyPressEventArgs parameter.

Example: A Keyboard Event Handler

private void searchTextBox_KeyDown(object sender, KeyEventArgs e)
{
    if (e.KeyData == Keys.Enter)
    {
        Console.WriteLine("Searching...");
    }
}

The KeyData property of the KeyEventArgs class stores the key code for the key that was pressed, along with any modifier key, such as Shift or Ctrl, that was held down at the same time.

🗂️ Managing Multiple Controls

TabStop and TabIndex

The Boolean TabStop property of a Control identifies whether that control will serve as a stopping place as the user presses the Tab key to move between controls. The numeric TabIndex property sets where in that sequence a given control falls.

If the TabIndex values of two or more controls on the same form are all set to 0, their tab order relative to each other becomes ambiguous; C# does not guarantee which of the tied controls receives focus first, since a clear, unique tab order depends on each control having a distinct TabIndex value.

The Enter Key and AcceptButton

When a Form has multiple GUI controls and the user presses Enter, the button assigned to that Form's AcceptButton property is usually activated automatically, exactly as if the user had clicked it directly. A thin, highlighted box conventionally drawn around whichever button is currently set as the Form's AcceptButton is what leads users to expect that pressing Enter will trigger that button's action.

Sharing One Event Handler Across Multiple Controls

A single event-handler method already written for one control can also be used to handle the same kind of event raised by a different control. In the Visual Studio Properties window, after clicking the small lightning bolt icon to view a control's list of available events, you can select the dropdown next to any specific event and choose an existing method already written for another control, rather than generating a brand-new handler.

If a single Control should raise several different events, each with its own distinct response, you can select that Control in Visual Studio, open the Events list using the lightning bolt icon in the Properties window, and then write separate action statements for each event you care about, one handler method per event.
