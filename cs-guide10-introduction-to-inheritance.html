Building New Classes from Existing Ones

Rather than writing every class completely from scratch, C# lets you build a new, more specific class on top of an existing, more general one, and automatically gain everything that existing class already offers. This guide covers how inheritance relationships are declared, how methods can be redefined in a more specific class, the root Object class every type ultimately descends from, how base class constructors fit into the picture, classes designed purely to be inherited from, interfaces, extension methods, and how inheritance shows up in GUI applications.

🌳 Inheritance Basics

Inheritance is the principle that lets a new class acquire the fields and methods of an existing class, then add its own more specific fields and methods on top of them. The existing class being built upon is called the base class, and the new class built from it is called the derived class.

It is the derived class, not the base class, that ends up containing everything: a derived class contains all the fields and methods of its base class, plus whatever additional, more specific fields and methods it defines itself. A base class does not automatically gain anything from classes derived from it.

Terminology Synonyms

C# literature uses several interchangeable pairs of terms for this same relationship.

Base Class Synonyms Derived Class Synonyms
Parent class Child class
Superclass Subclass
(no separate synonym) Extended class

Declaring an Inheritance Relationship

A derived class declares its base class using a single colon after the derived class's identifier, followed by the base class's name.

Syntax: Declaring a Derived Class

class Animal
{
    public string Name { get; set; }
}

class Dog : Animal
{
    public string Breed { get; set; }
}

Here, Dog is a derived class (or child class, or subclass) of the base class (or parent class, or superclass) Animal. A Dog object automatically has a Name property, inherited from Animal, in addition to its own Breed property.

Identifying Base and Derived Classes with "Is A"

One reliable way to check whether two classes truly have a base/derived relationship is to use them in a sentence on either side of the phrase "is a": "A Dog is an Animal" reads naturally and correctly, confirming that Animal belongs on the base class side and Dog belongs on the derived class side of the relationship.

Inheritance Is Transitive

Inheritance is transitive: a class inherits the members of every class above it in the inheritance chain, not just its immediate base class. If Puppy were derived from Dog, a Puppy object would inherit members from both Dog and, transitively, from Animal as well; every class further up the chain is considered one of its ancestors.

🔒 Protected Access

The protected access specifier makes a field or method usable within its own class and within any class derived from it, but not usable by any "outside," unrelated class. It sits between private, which blocks even derived classes, and public, which allows every class access.

Example: A Protected Field

class Animal
{
    protected string diet;
}

Changing a field's access from private to protected, as shown above, is exactly how you make a base class field accessible to its descendants while still keeping it inaccessible to unrelated classes.

Fragile Classes

A derived class that depends directly on a base class's specific field names, rather than going through properties or methods, is considered fragile: prone to breaking if the base class's author ever renames or restructures those fields, even in ways that would otherwise be a harmless internal change.

🎭 Polymorphism and Overriding

Polymorphism is using the same method name to produce different implementations depending on the specific class involved, such as one Play() method that produces a string of notes for a Violin and a different Play() method that produces a drum pattern for a Drum, even though both classes might share a common base class.

Virtual Methods and Overriding

To allow a derived class to redefine a base class method, that method must be declared virtual in the base class. The derived class then uses the override modifier to provide its own version.

Example: Overriding a Virtual Method

class Instrument
{
    public virtual void Play()
    {
        Console.WriteLine("An instrument makes a sound.");
    }
}

class Violin : Instrument
{
    public override void Play()
    {
        Console.WriteLine("The violin sings a melody.");
    }
}

When you declare a method in a derived class using override, matching a method that was declared virtual in the base class, that override completely replaces the base class's implementation with the derived class's own version whenever the method is called on an object of the derived class.

Overriding requires an identical signature: the same method name and the same parameter list. If a derived class defines a method with the same name as a base class method but a different parameter list, that is ordinary method overloading, not overriding; the two methods remain entirely separate rather than one replacing the other.

Hiding a Method with new

If a derived class defines a method with the exact same name and parameter list as a base class method, but the base class method was not declared virtual, the derived class's version hides the base version rather than overriding it. Adding the new keyword to the derived class method signals that this hiding is intentional, silencing the compiler warning that would otherwise appear.

Members That Are Not Hidden or Overridden

Any base class member that a derived class does not explicitly hide or override remains fully visible and usable in the derived class exactly as the base class defined it, inherited without any change at all.

Accessing the Base Class Version with base

The base keyword always refers to the superclass of whatever class it is used in, and it lets a derived class explicitly call the base class's own version of a method or property it has overridden.

Example: Calling the Base Class Version

class Violin : Instrument
{
    public override void Play()
    {
        base.Play();
        Console.WriteLine("The violin sings a melody.");
    }
}

Calling base.Play() here runs Instrument's original Play() implementation first, before Violin's own additional statement executes.

🔄 Implicit Reference Conversions

You can assign a derived class object to a variable of any of its base class types. C# performs this automatically through an implicit reference conversion, requiring no explicit cast at all.

Example: An Implicit Reference Conversion

Violin fiddle = new Violin();
Instrument someInstrument = fiddle;
// Legal without a cast: a Violin is an Instrument

This same conversion happens automatically whenever a derived class object is passed as an argument to a method whose parameter is declared using a base class type. A method with a parameter declared as Instrument can accept an argument of type Instrument, Violin, Drum, or any other class derived from Instrument, without the caller needing to write any explicit conversion.

You assign an object to its ancestor's type specifically whenever you pass a more specific, derived-class object into code, such as a variable or a method parameter, that expects a more general, base-class type; C# relies on the "is a" relationship to allow this conversion safely.

🌐 The Object Class

Every class you create in C# is ultimately derived from a single built-in root class: System.Object. The keyword object (lowercase) is simply an alias for System.Object. Because every class descends from Object, either directly or transitively through its ancestors, every object you create automatically has access to a small set of methods defined by Object itself.

When you create any C# object, you implicitly call the Object class's own constructor as part of that object's construction, even though you never write that call yourself; it happens automatically as the first step in building any object, since every class ultimately descends from Object.
Object Method Purpose
GetType() Returns a Type object representing the object's class, which can in turn provide the class's name
ToString() By default, returns a string containing the object's fully qualified class name; often overridden as a useful debugging aid to describe an object's contents instead
Equals() By default, tests for reference equality: whether two variables refer to the exact same object in memory, not merely equal values
GetHashCode() Returns an integer that acts like a fingerprint for the object, intended to uniquely identify it

Reference Equality

Two objects exhibit reference equality when they refer to the exact same memory location, meaning they are literally the same object rather than two separate objects that merely happen to hold identical field values. A call such as firstCoin.Equals(secondCoin), left unmodified, tests exactly this: it returns true only if firstCoin and secondCoin are references to the very same object, not simply two different objects with matching data.

Overriding ToString()

Overriding ToString() to describe an object's own data, rather than just its class name, is a common and useful debugging technique.

Example: Overriding ToString()

class Membership
{
    public int MemberID { get; set; }
    public string HolderName { get; set; }

    public override string ToString()
    {
        return string.Format("{0}: #{1}, {2}", GetType().Name, MemberID, HolderName);
    }
}

Calling GetType().Name inside ToString() retrieves just the class's simple name, "Membership," as a clean string, which is also the general technique for displaying an object's class name to a user without any extra namespace text attached.

Overriding Equals() and GetHashCode()

A correctly overridden Equals() method must still return bool, and it should accept a parameter of type object to properly match the signature it is overriding from the Object class; declaring it with a return type of int, or a parameter type matching only your own class, fails to correctly override Equals(object) at all. By convention, whenever you override Equals() to compare objects by value instead of by reference, you should also override GetHashCode() so that two objects considered equal always produce the same hash code.

🏗️ Base Class Constructors

A base class's constructor always executes before a derived class's own constructor. When you instantiate a derived class object, C# first runs the appropriate base class constructor, building the inherited portion of the object, before running any statements in the derived class's own constructor body.

Passing Arguments to a Base Constructor

If a base class does not provide an accessible parameterless constructor, a derived class must explicitly call one of the base class's constructors using : base(...) syntax, supplying whatever arguments that base constructor requires.

Example: Calling a Base Constructor

class Animal
{
    public string Name { get; set; }

    public Animal(string name)
    {
        Name = name;
    }
}

class Dog : Animal
{
    public string Breed { get; set; }

    public Dog(string name, string breed) : base(name)
    {
        Breed = breed;
    }
}
Because Animal here only defines a one-parameter constructor, and no parameterless constructor at all, Dog is required to write a constructor for itself and use : base(name) to satisfy Animal's constructor requirement. If Animal instead provided an accessible parameterless constructor, Dog would not be required to write any constructor of its own at all.

🧱 Abstract and Sealed Classes

Abstract Classes

An abstract class is a class from which you cannot create concrete objects, but from which you can still inherit. A class capable of being instantiated normally, by contrast, is called a concrete class. Mark a class abstract with the abstract keyword in its header.

Syntax: An Abstract Class

abstract class Instrument
{
    public abstract void Play();
}
Attempting new Instrument() against an abstract class is always a compiler error; abstract classes exist purely to serve as a foundation for derived, concrete classes to build on.

Choosing virtual vs. abstract

Declare a base class method virtual, rather than abstract, whenever the method should be overridden in some derived classes but not necessarily all of them; a virtual method always includes a working default implementation that a derived class is free to use as-is. An abstract method, by contrast, has no body at all in the base class and forces every derived class to supply its own implementation before it can be instantiated.

Sealed Classes

A sealed class is one that cannot be extended by any other class at all. Marking a class sealed prevents any further inheritance from it, which is exactly what prevents a class such as C#'s own System.Console from being extended by other code.

Syntax: A Sealed Class

sealed class FinalReport
{
    // No other class can inherit from FinalReport
}

🔌 Interfaces and Multiple Inheritance

An interface is a collection of purely abstract methods (and possibly other members), all without any implementation, that any class can use as long as it supplies its own working definition for every method the interface declares.

Syntax: Declaring an Interface

interface IPlayable
{
    void Play();
}

No Multiple Inheritance for Classes

C# prohibits multiple inheritance for classes: a class can have, at most, one base class. This differs from languages such as C++, where a class can inherit directly from more than one parent class at once. One major reason multiple inheritance causes problems is ambiguity: if two separate parent classes each define a member with the same name, there is no clear, unambiguous way to decide which parent's version a derived class should use.

While a C# class can only extend one base class, it can implement as many interfaces as needed at the same time. This gives C# a controlled, unambiguous alternative to multiple inheritance: a class inherits behavior from a single base class while also being required to fulfill the contracts of any number of interfaces.

Abstract Classes vs. Interfaces

An important distinction between the two: a class may extend only one abstract (or concrete) base class, but that same class may implement several interfaces simultaneously. Both abstract classes and interfaces can declare methods that derived or implementing classes must define, but only an abstract class can also supply fields, constructors, and fully implemented (nonabstract) methods alongside its abstract ones; an interface's methods are exclusively abstract.

🧵 Extension Methods

An extension method is a static method, written inside a static class, that can be called as though it were an instance method of a completely different, often preexisting, type. Extension methods can be described as static methods that are called like instance methods.

Syntax: An Extension Method

static class NumberExtensions
{
    public static double ToFahrenheit(this double celsius)
    {
        return celsius * 9 / 5 + 32;
    }
}

// Called as though ToFahrenheit() were a built-in double method:
double boilingPoint = 100.0.ToFahrenheit();
// boilingPoint is 212.0

The this keyword placed on the first parameter, this double celsius, is what marks ToFahrenheit() as an extension method and identifies exactly which type, double, it extends. The class containing an extension method must itself be declared static.

🖱️ GUI Application Inheritance

Every Form created inside the Visual Studio IDE inherits from the built-in Form base class. This is exactly the same inheritance mechanism covered throughout this guide, simply applied automatically by the IDE's project templates.

When Visual Studio generates a Form object for you, you can double-click it and examine its generated code to see exactly which class it inherits from. Its class header will read something like public partial class Form1 : Form, immediately revealing Form as that class's immediate ancestor, in exactly the same class Identifier : BaseClassName pattern used throughout this guide.
