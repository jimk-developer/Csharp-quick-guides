Teaching a Program to Choose

Every useful program eventually has to react differently depending on the data it receives. This guide covers how to plan that logic before you write a single line of code, how to write single- and dual-alternative decisions, how to build compound Boolean expressions with AND and OR, how switch structures handle many exact matches at once, the shorthand ternary operator, negating a condition, why an English request does not always translate into the operator it seems to name, and the habits that keep decision-making code correct and readable.

🗺️ Planning Program Logic

Before typing any C# code, experienced programmers often plan a program's logic on paper or in a diagram. Two common planning tools are pseudocode and flowcharts.

📝 Pseudocode

Plain English statements that describe the steps a program will take, written in a structured, step-by-step way without worrying about exact C# syntax.

📊 Flowchart

A diagram that represents program logic visually, using standardized shapes connected by arrows that show the order steps occur in.

Flowchart shapes carry specific meanings. To represent a decision, flowchart creators use a diamond shape to hold a question, and they draw paths to the alternative courses of action emerging from the corners of the diamond.

Shape Represents
Diamond A decision — a question with alternative courses of action leading away from it
Parallelogram An input or output statement, such as reading a value from the user or displaying a result
Rectangle A processing step, such as a calculation or an assignment
Flowline An arrow connecting shapes to show the order in which steps occur

You can create a meaningful flowchart using only rectangles, diamonds, and flowlines, but parallelograms have traditionally been used to set input and output statements apart from other processing.

Sequence Structures vs. Decision Structures

Structure Description
Sequence structure Indicates that one step follows another unconditionally, with no branching or choice involved
Decision structure Involves choosing between alternative courses of action based on some value within the program

These are the only two names you need here. Any structure in which a condition determines whether a step is taken, or which of several alternative steps is taken, is a decision structure — so terms like "single-decision," "dual-decision," and "branched" all describe kinds of decision structures, never a sequence structure. A sequence structure may contain any number of steps, but one task follows another with no chance to branch away or skip a step. Note also that "literal" and "fixed" are not structures at all; a literal is a type of value, such as the number 5.

All Computer Decisions Are True-or-False Decisions

When reduced to their most basic form, every decision a program makes is a true-or-false decision. Program code never asks an open question like "What number did the user enter?" Instead it asks a series of yes-or-no questions: "Did the user enter a 1?" "If not, did the user enter a 2?" "If not, did the user enter a 3?"

A control statement is any statement that determines the order in which other statements execute. The if expression that precedes a block in a decision structure is the control statement for that structure, because it controls the flow of program logic at that point in execution. Note the distinction in vocabulary: sequence and decision are types of structure, while if and if-else are types of statement.

🔀 Single-Alternative Decisions

The if Statement

A single-alternative decision executes one or more statements only when a condition is true, and otherwise simply moves on to whatever comes next. In C#, you write this using an if statement: an expression, evaluated as true or false, that precedes a block in a decision structure.

Syntax: A Single-Alternative if Statement

if (orderTotal > 100)
{
    Console.WriteLine("You qualify for free shipping.");
}

Blocks

A block is a collection of one or more statements contained within a pair of curly braces. If you want to execute two or more statements when a condition is true — and simply move on to the next unit of code when it is false — those statements must be placed within a block. Blocking them with braces is the only way to make multiple statements depend on a single if.

It is perfectly legal, though not required, to use a block around even a single statement. Creating a block that contains no statements at all is also legal in C#. Blocking a single statement that depends on an if is a useful habit, because when the program is later modified to include multiple dependent statements, the braces are already there as a reminder to use a block.
Indentation alone does nothing. The C# compiler pays no attention to indentation, so indented statements that are not enclosed in braces do not depend on the if at all. In the code below, the second WriteLine looks like part of the decision, but it is a separate statement that executes no matter what the user enters.

Example: Misleading Indentation Without Braces

if (pizzaDiameter == 8)
    Console.WriteLine("You will get 4 slices.");   // depends on the if
    Console.WriteLine("8-inch pizzas bake faster.");  // ALWAYS executes

Nested if Statements

A nested if statement is a single-alternative decision structure contained within another one. Nesting lets a program test a second condition only after the first condition has already been satisfied.

Example: A Nested if Statement

if (isMember)
{
    if (purchaseTotal >= 50)
    {
        Console.WriteLine("You earned bonus points.");
    }
}
When if-else statements are nested, each else is always paired with the closest, most recent if that does not already have an else attached to it, regardless of how the code happens to be indented. Misleading indentation can make a nested if-else read incorrectly even though the compiler pairs it correctly.

Assignment vs. Equivalency

A condition that tests for equality must use the equivalency comparison operator (==), not the single assignment operator (=). Writing if (x = 5) instead of if (x == 5) does not compare x to 5; it attempts to assign 5 to x, and in C# this specific mistake with a numeric variable inside an if condition fails to compile, because an if condition must evaluate to a bool, not an int.

⚖️ Dual-Alternative Decisions

A dual-alternative decision performs one action when a Boolean expression evaluates to true and a different action when it evaluates to false. C# implements this with an if-else statement.

Syntax: An if-else Statement

if (orderTotal >= 50)
{
    Console.WriteLine("You qualify for free shipping.");
}
else
{
    Console.WriteLine("Shipping costs $5.");
}

Exactly one of the two branches executes every time an if-else statement runs; there is no possibility that both branches, or neither branch, will execute.

➕ Compound Expressions with AND

A compound Boolean expression tests more than one condition at once. The conditional AND operator (&&) combines two Boolean expressions so that the overall expression is true only when both sides are true, offering a more concise alternative to writing nested if statements.

Example: Conditional AND

if (isMember && purchaseTotal >= 50)
{
    Console.WriteLine("You earned bonus points.");
}

This single if statement accomplishes the same result as the nested if example shown earlier, but in one line instead of two nested blocks.

Short-Circuit Evaluation

C#'s conditional operators use short-circuit evaluation: each part of a compound expression is evaluated only as much as necessary to determine the overall result. With &&, if the left-hand expression is false, the right-hand expression is never evaluated at all, since the overall result is already known to be false.

Short-circuit evaluation is more than a performance detail. It is common practice to place a safety check on the left side of &&, such as confirming an object is not null, so that the right side is never evaluated unless the left side has already guaranteed it is safe to do so.

The and and is Keywords (C# 9)

Starting with C# 9, you can express certain AND conditions using the and keyword together with is, particularly when testing whether a single value falls within a range.

Example: Range Test with is and and

// Traditional compound expression
if (age >= 13 && age <= 19)
{
    Console.WriteLine("Teenager");
}

// C# 9 pattern-matching equivalent
if (age is (>= 13 and <= 19))
{
    Console.WriteLine("Teenager");
}

Both statements above test the same range and produce the same result. Note the parts of the pattern form: the variable name, then the keyword is, then the comparisons joined by and, enclosed in parentheses. The is keyword is required — leaving it out is an error, and so is attaching the comparison group directly to the variable name, as in if (age(>= 13 and <= 19)). The parentheses around the comparison group are the conventional way to write this pattern and are used throughout this guide.

✔️ Advantage of and

You do not have to write a complete Boolean expression on both sides of and. The variable name appears only once, which sometimes makes the code more concise.

⚠️ Disadvantage of and

You must use the extra keyword is. And there is no performance benefit — short-circuit evaluation is used with either format, so the choice is purely about readability.

🔀 Compound Expressions with OR

The conditional OR operator (||) combines two Boolean expressions so the overall expression is true if at least one side is true. Use it whenever an action should occur as long as any one of several conditions holds.

Example: Conditional OR

if (hasCoupon || orderTotal > 100)
{
    Console.WriteLine("A discount has been applied.");
}

Short-circuit evaluation applies to || as well, but in the opposite direction from &&: if the left-hand expression is already true, the right-hand expression is never evaluated, because the overall result is already known to be true.

Note the division of labor between the two conditional operators. Only && can replace nested if statements, because nesting requires every condition to hold before the dependent statement runs. The || operator expresses the opposite idea — that any single condition is enough — so it cannot substitute for nested ifs. Neither can the XOR operator described in the next section.

The or and is Keywords (C# 9)

C# 9 offers a similar pattern-matching alternative for OR conditions using or with is, useful when comparing one variable against several possible values or an excluded range.

Example: OR Pattern with is and or

// Traditional compound expression
if (ticketCount < 1 || ticketCount > 10)
{
    Console.WriteLine("Invalid quantity.");
}

// C# 9 pattern-matching equivalent
if (ticketCount is (< 1 or > 10))
{
    Console.WriteLine("Invalid quantity.");
}
The advantages and disadvantages of or match those of and: it is more concise because you do not need a complete Boolean expression on both sides, but it requires the extra is keyword and offers no performance gain. This is especially useful when an if statement compares the same variable against several other values or variables. Instead of repeating the variable name in every comparison, write it once before is, then list just the comparison operator and value for each part, separated by or.

Example: One Variable, Several Comparisons

// Repetitive version
if (size == SMALL || size == MEDIUM || size == LARGE)

// More concise C# 9 equivalent
if (size is (== SMALL or == MEDIUM or == LARGE))
Conciseness is the only thing the or pattern buys you here. Swapping || for the non-conditional | operator is sometimes possible — as long as losing short-circuit evaluation would not cause a side effect — but it does nothing to shorten the code, since the variable name still has to be repeated in every comparison.

🔧 Logical vs. Conditional Operators

C# also provides a Boolean logical AND operator (&) and a Boolean logical inclusive OR operator (|). Visually similar to && and ||, these single-character versions behave differently in one important way: they do not support short-circuit evaluation. Every part of the expression is always evaluated, even when the overall result is already determined by the first part. Because they lack that behavior, & and | are sometimes called the non-conditional operators, in contrast to the conditional operators && and ||.

Because the logical AND and logical OR operators always evaluate both sides, they can introduce side effects: unwanted or unintended consequences that happen because a second expression ran when it did not need to. If the right-hand expression calls a method that changes program state or could throw an exception when its left-hand guard condition is false, using & or | instead of && or || can cause that method to run in a situation the programmer never intended.

When the & and | operators are used between two integer expressions rather than two Boolean expressions, they are called bitwise operators, and they are used to manipulate the individual bits of values, performing a bit-by-bit comparison of the two integers' underlying binary representations instead of any Boolean logic.

Because && and || do use short-circuit evaluation, an ordinary compound condition built from the conditional operators — such as if (hasCoupon || isVeteran || age >= 65) — does not pose a high risk of side effects. Side effects are a concern with the single-character & and | operators.

The Logical Exclusive OR (XOR) Operator

C# also has a logical exclusive OR, or logical XOR, operator, written as a caret (^). For any two expressions x and y, the expression x ^ y is true only if one of the expressions is true and the other is false, which makes it work much like the inequality operator. XOR is not a conditional operator, and it cannot substitute for nested if statements the way && can.

📐 Combining AND and OR

You can combine as many && and || operators together in a single expression as a program requires.

Expression Contains Order of Evaluation
A series of only && or only || operators Evaluated from left to right, as far as is necessary to determine the value of the entire expression
&& and || mixed in the same expression Not necessarily left to right. The && operators take precedence, meaning they are evaluated first — the same way multiplication is evaluated before addition in arithmetic

Parentheses can always be added to make the intended grouping explicit and easier to read. More importantly, parentheses override the default precedence, so they are how you force an OR condition to be evaluated before an AND condition.

Example: Mixing AND and OR

if (isMember && orderTotal > 75 || hasFreeShippingCode)
{
    Console.WriteLine("This order ships free.");
}
// Equivalent, with the default precedence made explicit:
if ((isMember && orderTotal > 75) || hasFreeShippingCode)

Using Parentheses to Override Precedence

Suppose students may skip the final exam if (1) they either attended all class sessions or completed an extra credit project, and (2) their current grade is at least 90. Because && takes precedence, the OR condition must be placed in parentheses to match that requirement.

Example: Parentheses Change the Meaning

// CORRECT - the OR test happens first, then the grade must also pass.
if ((hasPerfectAttendance || hasExtraCredit) && grade >= 90)
{
    Console.WriteLine("Eligible to skip final exam");
}

// WRONG - without the parentheses, && binds first, so this reads as
// hasPerfectAttendance || (hasExtraCredit && grade >= 90).
// A student with perfect attendance and a grade of 50 would qualify.
if (hasPerfectAttendance || hasExtraCredit && grade >= 90)
Adding parentheses around the && portion — hasPerfectAttendance || (hasExtraCredit && grade >= 90) — changes nothing at all, because && was already going to be evaluated first. Only parentheses placed around the || portion actually alter the order of evaluation.

Truth Tables

A truth table is the best tool for working out every possible outcome of a compound Boolean expression. It is a diagram used in mathematics and logic that describes the truth of an entire expression based on the truth of its parts: each row represents a different combination of true and false values for the parts of the expression, alongside the overall result that combination produces.

x y x && y x || y
true true true true
true false false true
false true false true
false false false false

Reading down the columns confirms the two rules in a single glance: x && y is true only when both parts are true, and x || y is false only when both parts are false. A flowchart, by contrast, shows the actions taken once an entire expression evaluates to true or false; it does not show how the smaller expressions inside a compound expression combine to produce that final result, which is why a truth table is the better tool for this particular job.

🔢 Switch Structures

A switch structure tests a single variable, known as the governing type once its data type is established, against a series of exact matches. A switch structure is often clearer than a long chain of if-else statements when a variable might equal any one of several specific values.

Example: A Switch Structure

switch (seatClass)
{
    case 1:
        Console.WriteLine("Economy seating.");
        break;
    case 2:
        Console.WriteLine("Premium seating.");
        break;
    case 3:
        Console.WriteLine("First class seating.");
        break;
    default:
        Console.WriteLine("Please choose seat class 1, 2, or 3.");
        break;
}
Read the anatomy of the example above carefully. The case labels — case 1:, case 2:, case 3: — are the lines that identify which course of action the structure takes, because they hold the values compared against the switch expression. The WriteLine lines are the actions themselves, and the break lines exit the structure; neither of those determines which path is chosen.
Keyword Purpose
switch Begins the decision structure and names the variable being tested, called the switch expression
case Followed by one possible value that might equal the switch expression, then a colon. The whole expression — for example, case 1: — is a case label, and it is the case labels that identify which course of action the structure takes
break Ends a case section so execution jumps out of the switch structure entirely
default Specifies the action to take when the test expression does not match any case. default: is not a case label, because it names no value to match
The default label is optional. If the switch expression does not match any case label and there is no default section, the program simply continues with the next executable statement after the switch structure. Even so, it is usually considered good programming practice to include a default label.
The "no fall-through rule." Every case section must end in a way that clearly exits the switch structure — most often with break, though return or throw can also end a case. The keyword break is by far the most commonly used. If C# reaches the end of a case section's statement list without hitting one of these, the compiler produces an error. Not allowing code to reach the end of a case that contains one or more statements is known as the no fall-through rule. In this respect C# differs from languages such as Java and C++, where writing a case without a break lets all subsequent cases execute until a break is encountered.

Using an Enumeration with a Switch

An enumeration, which begins with the enum keyword, allows you to apply values to a list of constants. Case label values become much clearer when used together with an enumeration instead of plain numbers, since each case then reads as a self-documenting name rather than an unexplained integer.

Example: Switch with an Enumeration

enum SeatClass { ECONOMY, PREMIUM, FIRST_CLASS }

SeatClass selectedClass = SeatClass.PREMIUM;

switch (selectedClass)
{
    case SeatClass.ECONOMY:
        Console.WriteLine("Economy seating.");
        break;
    case SeatClass.PREMIUM:
        Console.WriteLine("Premium seating.");
        break;
    case SeatClass.FIRST_CLASS:
        Console.WriteLine("First class seating.");
        break;
}

Assigning Integer Values and Casting User Input

You can assign specific integer values to the constants in an enumeration. When a user enters an integer, that value can be cast to an enumeration value inside the switch control statement; the enumeration values then become the governing types for each case.

Example: Enumeration Values Applied to Constants

// Applies integer values to a list of constants:
// RED is 1, BLUE is 2, YELLOW is 3, WHITE is 4.
enum Color { RED = 1, BLUE, YELLOW, WHITE }

int color = Convert.ToInt32(Console.ReadLine());

// The entered integer is cast to an enumeration value.
switch ((Color)color)
{
    case Color.RED:
        Console.WriteLine("You chose red.");
        break;
    case Color.BLUE:
        Console.WriteLine("You chose blue.");
        break;
    default:
        Console.WriteLine("Unrecognized choice.");
        break;
}
When a program repeatedly uses || to compare the same variable against several different exact values, that chain of OR comparisons can usually be rewritten as a switch structure, which reads more clearly once there are more than two or three values to check.

❓ The Conditional (Ternary) Operator

The conditional operator, also called the ternary operator because it requires three arguments, provides an abbreviated way to write a simple if-else statement. Its three arguments are a test expression, a result to use when the test is true, and a result to use when the test is false.

Syntax and Example: The Ternary Operator

// General form
// testExpression ? trueResult : falseResult;

int customerAge = 15;
double ticketPrice = customerAge >= 12 ? 15.00 : 5.00;
// ticketPrice is assigned 15.00, since customerAge is 15

The characters ? and : together form the ternary conditional operator. The statement above is functionally identical to a full if-else statement that assigns 15.00 in the true branch and 5.00 in the false branch, just written in a single line.

Counting Operands: Unary, Binary, and Ternary

Operators in C# are classified by how many operands, or arguments, they require. The conditional operator ?: is the only ternary operator in C#.

Classification Operands Examples
Unary One !isTaken, -price
Binary Two, one on each side of the operator a + b, x != y, p && q
Ternary Three: a test expression, a true result, and a false result age >= 12 ? 15.00 : 5.00

Using the Conditional Operator Inside Output

The conditional operator is most often applied when you want to use the result as an expression — for example, by displaying it — without creating an intermediate variable. Placed inside an interpolated string, the whole conditional expression must be wrapped in parentheses within the braces, and each string result keeps its own quotation marks.

Example: A Ternary Expression in an Interpolated String

// CORRECT
Console.WriteLine($"{(orderTotal >= 50 ? "Free shipping" : "$5 shipping")}");

// WRONG - quotation marks omitted around the results,
// so the compiler reads them as invalid identifiers.
// WriteLine((orderTotal >= 50) ? Free shipping : $5 shipping);

// WRONG - the ? and : symbols appear in the wrong order.
// WriteLine((orderTotal >= 50) : "Free shipping" ? "$5 shipping");
Order matters and is easy to get backwards. The result before the colon is used when the test is true, and the result after the colon is used when it is false. Swapping the two produces code that compiles cleanly but displays the wrong message — a logical error rather than a syntax error.

🚫 Negation

The NOT operator (!) reverses, or negates, the result of any Boolean expression: a true expression becomes false, and a false expression becomes true.

Example: The NOT Operator

bool seatIsTaken = true;

if (!seatIsTaken)
{
    Console.WriteLine("This seat is available.");
}

The ! Operator vs. the != Operator

These two operators look related but are used very differently. An exclamation point followed by an equal sign forms the "not equal to" comparison operator, which is a binary operator: it compares two operands. An exclamation point that is not followed by an equal sign is the NOT operator, a unary operator that reverses the meaning of a single Boolean expression.

Some other programming languages use <> to mean "not equal to," but <> is not an operator in C# at all. The two characters are used separately as the relational operators "less than" and "greater than."

Negating Comparisons Directly

Rather than wrapping a comparison in !(...), it is often clearer to rewrite the comparison using its opposite operator. For example, !(temperature < 80) means exactly the same thing as temperature >= 80, and !(pressure <= 30) means the same thing as pressure > 30. Applying this to a compound expression, !(a) && !(b) can be rewritten directly as the AND of each comparison's opposite, without changing what the overall expression evaluates to.

The is not Syntax (C# 9)

Starting with C# 9, you can replace the ! operator with the is not pattern without changing how the code functions, which some programmers find easier to read aloud as ordinary English. The keyword not must always be used together with the keyword is; not cannot stand in for ! on its own.

Using is not may be easier for a human reader to understand, but it makes no difference whatsoever to the compiler. It is not faster, and it does not make the code easier for C# to process. The only advantage is readability.

Example: is not with a Range

// Produces output when num falls OUTSIDE the range LOW through HIGH.
if (num is not (>= LOW and <= HIGH))
{
    Console.WriteLine("Value is out of range");
}

Example: ! vs. is not

// Using the NOT operator
if (!seatIsTaken)
{
    Console.WriteLine("This seat is available.");
}

// Equivalent using is not
if (seatIsTaken is not true)
{
    Console.WriteLine("This seat is available.");
}

✅ Decision-Making Best Practices

Range Checks and Range Matches

A range check is a series of if statements that determines whether a numeric value falls between specified maximum and minimum values, most often written as an if-else if chain when the ranges are not exact, individual values. A closely related idea, a range match, tests a value against a set of defined ranges to determine which one it falls into, typically to assign a different result for each range.

Example: A Range Match with if-else if

int customerAge = 8;
double entryFee;

if (customerAge <= 2)
{
    entryFee = 0;
}
else if (customerAge <= 11)
{
    entryFee = 12;
}
else
{
    entryFee = 20;
}
Once a range check finds the correct range, later conditions in the chain are never even tested; each else if only runs when every prior condition was false. This is exactly why the example above only needs to test the upper bound of each range: by the time execution reaches the second condition, the value has already been confirmed to be greater than 2.

Writing a Correct and Efficient Range Check

New programmers frequently introduce incorrect or inefficient code when writing range checks. Two rules prevent almost all of these errors. First, use the if…else if…else pattern rather than a series of separate if statements. Second, for efficiency, begin with the condition that is most likely to be true, and never test a condition that has already been established by elimination.

✔️ Correct and Efficient

if (customerAge >= 12)
    entryFee = 20;
else if (customerAge >= 3)
    entryFee = 12;
else
    entryFee = 0;

⚠️ Works, but Wasteful

if (customerAge >= 12)
    entryFee = 20;
else if (customerAge >= 3)
    entryFee = 12;
else if (customerAge < 3)
    entryFee = 0;

The final test is unnecessary. If the age is not 3 or greater, it must be less than 3.

Separate if statements are the classic mistake. Replacing the else if clauses above with three plain if statements breaks the logic, because each one is tested regardless of what came before. After if (customerAge >= 12) entryFee = 20; correctly assigns 20, the next statement if (customerAge >= 3) entryFee = 12; is also true for that same customer and overwrites the value with 12. The else keyword is what stops execution from continuing through the rest of the chain.
Two structures are poor choices for range checks. Nested if statements do not work well because when the outermost condition is false, none of the inner conditions are checked at all. A switch structure is usually inappropriate because it tests for exact matches, meaning you would need a separate case label for every individual value in the range — unmanageable for anything more than a handful of values.

Common Syntax Errors to Avoid

⚠️

Stray Semicolon

Placing a semicolon directly after an if condition, such as if (total > 100);, creates an empty statement. The block that follows then always executes regardless of the condition, since it is no longer connected to the if at all.

⚠️

Incomplete Comparisons

Each side of && or || needs its own complete Boolean expression. Writing size == 1 || 2 does not test whether size equals 1 or 2; it must be written as size == 1 || size == 2.

Brace Placement Style

In C#, it is customary to align a block's opening and closing braces, each on its own line. Some programmers prefer to place the opening brace on the same line as the if expression instead. That style is called K & R style, named for Brian Kernighan and Dennis Ritchie, who wrote the first book on the C programming language.

K & R Style

if (total > 100) {
    discount = 10;
}

Allman Style

if (total > 100)
{
    discount = 10;
}

Allman style places braces on their own line, as the examples throughout this guide do. A third convention, GNU style, uses broken braces with indented blocks. All of them compile identically; the choice is a matter of team convention and readability preference, not a functional difference.

🗣️ When Language Does Not Match Logic

One of the most common sources of logical errors in decision making has nothing to do with C# syntax at all. Everyday English often describes a condition in words that do not translate directly into the operator you actually need. The word "and" in a request very frequently calls for the || operator in the code.

English "and" Often Means OR in Logic

Consider this request: "Display a promotional code to a website visitor when they place an item in the shopping cart and when they click on the 'Sale' tab." Although the request says "and," it describes two separate situations in which the same action should occur. Only one of them has to be true, so the logic requires an OR operator.

Example: "Pink and Purple Items" Needs ||

// Request: "Change the discount to 0.25 for pink and purple items."

// WRONG - itemColor can never be both strings at once,
// so discount is never changed.
if (itemColor == "pink" && itemColor == "purple")
    discount = 0.25;

// CORRECT - either color qualifies.
if (itemColor == "pink" || itemColor == "purple")
    discount = 0.25;

// Also correct, using the C# 9 pattern form:
if (itemColor is (== "pink" or == "purple"))
    discount = 0.25;
Sometimes the two things joined by "and" in English are mutually exclusive, which means a condition written with && can never be true. For the English statement "Display the names of employees in departments 1 and 2," the statement if (department == 1 && department == 2) would never display any name at all, because a single employee's department cannot be both values at the same time. Note that substituting the logical & operator for && does not help; the condition is still impossible.

Using NOT Correctly in Compound Decisions

Negated compound conditions are the other classic trap. When a requirement says a value must not be either of two values, each individual comparison must be joined with &&, not ||.

Example: "Not Either R or C"

// Request: change taxRate to 0.09 when taxStatus is not R and not C.
double taxRate = 0;

// CORRECT - both comparisons must be true.
if (taxStatus != 'R' && taxStatus != 'C')
    taxRate = 0.09;

// WRONG - this is true for EVERY possible value of taxStatus.
if (taxStatus != 'R' || taxStatus != 'C')
    taxRate = 0.09;
Look closely at why the second version above is always true. If taxStatus holds 'R', then taxStatus != 'C' is true, so the whole OR expression is true. If it holds 'C', then taxStatus != 'R' is true, so the expression is true again. Any other character makes both sides true. An expression of the form x != a || x != b can never be false, so the dependent statement always executes.

The same reasoning applies to an English statement such as "Set the ticket price to $50 when the seat is not in section 1 or section 2." Written as if (seatSection != '1' || seatSection != '2'), the price would be set to $50 for every seat in the stadium, including sections 1 and 2 — the exact opposite of the intent. Two correct versions are shown below.

Example: Two Correct Ways to Write "Not 1 or 2"

// Negate the whole compound OR expression:
if (!(seatSection == '1' || seatSection == '2'))
    ticketPrice = 50;

// Or distribute the negation, changing || to &&:
if (seatSection != '1' && seatSection != '2')
    ticketPrice = 50;
The rule to remember: negating a compound expression flips its operator. Not (A or B) becomes (not A) and (not B); not (A and B) becomes (not A) or (not B). Whenever a requirement contains the word "not" together with "or," expect && to appear in the finished code.

🖱️ Decisions in GUI Applications

The decision-making structures covered in this guide apply just as directly inside GUI event-handling methods as they do in console programs. However, event-driven programs often require fewer coded decisions than console applications, not more.

Why GUI Programs Often Need Fewer Decisions

In an event-driven program, some events are determined by the user's actions while the program is running (during runtime) rather than by the programmer's coding beforehand. In a GUI application, you are more likely to place controls on a Form than to ask the user to type in data. The user clicks a Button and the appropriate method executes. No decision has to be written in the program at all, because a different event is fired from each Button, causing execution of a different Click() method.

🖥️ Console Version

The program prompts the user to enter 1 or 2, then needs an if-else or switch structure to determine which value was entered and what to do about it.

🖱️ GUI Version with Buttons

Two Buttons are placed on the Form. Clicking each one fires its own event and runs its own Click() method, so no decision statement is needed to tell the choices apart.

In a GUI application, decisions are typically used when users enter data — such as an integer typed into a TextBox — that the program must act on. If you place a TextBox on a Form and ask a user to enter a 1 or a 2, the decision-making process becomes identical to that of the console-based program. Using controls such as Buttons that limit the selections a user can make is a separate technique for preventing invalid entries; it reduces the need for coded decisions rather than creating it.
Watch the word always in statements about this topic. It is not true that event-driven programs always require more coded decisions than console applications in order to handle invalid user entries. The opposite is usually the case, because well-chosen controls remove the need for many decisions entirely.
